# Qwen3.5-9B 实验独立分析

现有数据足以支撑“前缀缓存管理模块的设计、实现与有边界的实验评估”作为本科毕设；尚不足以宣称通用加速或并发正确性已被证明。reuse2 在混合负载的三个种子上均有小幅收益，在热点扫描上收益不稳定。最需要补齐的是并发输出差异的原因和模块契约，而不是继续扩大参数搜索。

本文由 Astra 独立读取 `run.json`、`requests.jsonl` 和源码快照复算，未采用 README 的结论。数据版本为 Git 提交 `866cdf5ca7b9177da76bbff8b07a77679a4b92f1`，目录 `data/public/nineb-opening-20261002`。

## 一、口径与完整性

正式样本仅为 `opening-round-v2/run-00` 至 `run-24`：11组成对 A/B 加3次 stock 重复。复核共12,800条请求，均成功且输出128 token；校准、诊断及 `selected-calibration` 副本未混入正式统计。固定 Qwen3.5-9B BF16，revision 为 `c202236235762e1c871ad0ccb60c8ee5ba337b9a`。平台标注 vGPU 32GB，设备名称显示 RTX 4080 SUPER，可见显存32,760MiB；这不能用于推断零售物理显卡规格。

命中率为总 cached_tokens / 总 prompt_tokens，差值使用百分点（pp）。p95 依原协议取排序后第 floor(0.95×(n−1)) 项。时长取客户端测量 duration_s，包含队列排空，不含模型启动；TTFT 从发送请求计时，TPOT 是首末 token-ID 流块间隔除以127。arrival_to_first_token 从计划到达计时，包含客户端积压。

混合负载的命中提升分别为3.8255、3.8256、0.8694pp，测量时长缩短2.6257%、2.6694%、0.5351%；TPOT p95均下降，但TTFT p95仅一个种子改善。因此不能把“命中提高”直接写成“首字尾延迟全面下降”。热点时长变化为−0.5247%、+0.4589%、−0.2908%，方向不一致。

热点种子0将缓存从1.5增至3、8GiB，两种策略都提高命中并缩短时长；reuse2在1.5GiB反而慢0.7864%，说明保留热点也可能挤走有用块。8→16并发时，stock实际输出吞吐从169.359升至225.161 token/s，而TPOT p95从41.625升至65.386ms：吞吐和单请求解码延迟存在取舍。2K输入时stock为213.632 token/s，候选为214.973 token/s；其prompt token分母和可缓存结构不同，不能仅按命中百分比判优劣。

这些是固定到达率4请求/s下的实际吞吐，绝非最大服务容量。所有配置均有明显积压：正式成对arrival p95为152.673—385.937秒，发送后的TTFT却只有约0.668—2.004秒。只报TTFT会掩盖用户在客户端等待的时间。容量、并发、输入长度的附加条件各只有一个种子，不能据此估计普遍收益。

## 三、输出一致性与证明边界

按 request_id 对齐，而非按JSONL行序比较输出token-ID哈希。三次追加A/A彼此512/512一致；但各自与最初stock run-00均有77/512差异，且512条缓存命中token数全部相同。run-00与三次A/A测量时长为386.964、386.996、387.030、387.041秒。性能高度接近不等于输出完全相同。

A/B共享前缀条件有89—203条输出差异，大部分发生于命中数相同组。stock自身发生过差异，说明基线也有敏感性，却不能排除候选的缓存错误；A/B差异也不能直接认定为错误。当前缺少首个分歧token、数值差异、批次轨迹与缓存状态证据，无法区分数值/调度敏感性和状态恢复问题。

受控串行对照64/64输入与输出哈希匹配，双方cached_tokens均129,360；候选选块1,324次、真正重排139次。因此覆盖了“确实执行重排”的串行路径。边界诊断12/12输入输出匹配，双方命中3,696 token；它支持已测边界案例，不是所有边界的证明。无复用对照512/512输出匹配、命中均为0且重排0次，只证明该退化路径没有观察到输出变化，不能证明复用重排的正确性。

## 四、工程价值与下一步

源码表明reuse2对空闲队列最多扫描32块，以复用次数阈值2调整分配顺序，随后交给原生分配逻辑；这是轻量保留原型，不是完整Marconi，也没有实现新的检查点放置算法。正式候选的 selection_cpu_ns合计每轮为0.165—0.447秒；计时器实际使用perf_counter_ns，覆盖选块段的耗时，未覆盖lookup计数、清理、reset及原生分配，不能写成“模块全部CPU开销”，更不能直接据此推算端到端净收益。

确定的是模块已运行、能改变缓存保留和命中，混合负载出现三个同向种子结果，且具备可追溯的测量与诊断。待证的是并发语义正确性、收益可推广性和完整资源开销。每类主负载只有3个成对种子；512请求共享缓存与队列，不能当作512个独立样本，也不应报告强总体置信区间。

毕设题目《面向混合注意力模型的前缀缓存管理模块设计与实现》可成立，贡献应落在模块接口、状态生命周期、保护约束、可观测性及条件性收益。后续优先三项：一是对既有分歧请求定位首个不同token，记录批次与缓存恢复状态，形成最小并发复现；二是固化分配、引用计数、清理与重置契约及回退路径；三是补全模块耗时与元数据内存统计。完成这些，比再铺一轮大规模参数实验更能增强论文可信度。
