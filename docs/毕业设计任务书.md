# 毕业设计任务书

- **题目**：面向混合注意力模型的前缀缓存管理模块设计与实现
- **实现平台**：vLLM，当前原型锁定版本为 0.30.0
- **正式实验主模型**：Qwen3.5-9B，纯文本 BF16，固定权重 revision 见[固定实验配置](固定实验配置.md)
- **文档状态**：开题前草案；已完成初步实验，正式管理模块待开发
- **更新日期**：2026-10-01

## 一、课题背景与目标

在文档问答、多轮对话等场景中，多个请求经常共享相同的输入前缀。保存前缀的中间计算结果，可以减少后续请求的重复计算。显存容量有限时，推理引擎需要回收部分缓存；若高复用的内容被低复用内容挤出，后续请求就需要重新计算。

混合注意力模型同时使用全注意力层和循环状态类层，其前缀复用涉及注意力 KV 与状态检查点。管理模块需要理解缓存组、可复用边界和对象生命周期，正确调用引擎的分配、查找、回收与重置流程。

本课题在真实 vLLM 上设计并实现一个前缀缓存管理模块，支持策略切换、保留信息维护及行为观测。重点解决受限缓存容量下的保留与淘汰问题，通过可复现的对照评测说明策略的作用、开销和适用边界。

**通俗说明**：模型读过的内容如果以后还要用，就尽量保留下来；空间不够时，根据复用价值决定先清理哪些缓存。

## 二、主要工作内容

### 1. 梳理混合模型缓存的数据路径

阅读锁定版本的 vLLM 代码，梳理请求前缀查找、缓存登记、空闲块回收和重置流程；记录注意力 KV、状态检查点及缓存组之间的关系。形成一张数据路径图，说明哪些对象可以参与淘汰选择。

### 2. 设计并实现缓存管理模块

- 提供原版策略与候选策略的统一切换入口、配置及版本检查。
- 管理缓存的复用记录和保留信息，处理淘汰、重置、对象再分配时的信息清理。
- 仅选择引擎允许回收的空闲对象，保留原生引用计数、哈希移除和缓存组匹配规则。
- 对候选扫描数量、附加记录数量和管理开销设置明确上限；不适用的路径回退到原生处理。

### 3. 实现并整合保留策略

已有 `reuse2` 原型按照实际复用次数调整空闲缓存块的回收顺序，可作为基础策略和对照。后续重点参考 Marconi 对复用可能性、可节省计算量和内存成本的考虑，完成至少一种可解释、可配置的保留策略。

结合工程中发现的问题处理热点变化、长期保留和冷请求开销等情况。引用论文思路时，写明实现内容及与原论文的差异；当前原型属于基于复用次数的轻量策略。

### 4. 完成观测与验收评测

采集请求级命中、生成耗时及必要的块级登记、移除事件；将诊断模式与计时模式分开。使用固定请求序列对照原版和候选策略，覆盖热点与一次性请求混合、文档热度不均及缓存充足三种场景，补充无复用请求的开销检查。

评测用于检查模块正确性、开销和适用边界。按实际发现的问题补充必要对照，保存每个结论对应的配置、代码版本与原始记录。

## 三、基本要求与完成标准

1. 在真实 vLLM 和至少一个混合注意力模型上运行完整模块，提供可复现的环境与启动说明。
2. 能切换原版与至少一种候选保留策略，讲清策略依据、介入位置和执行边界。
3. 正确维护保留信息的生命周期和缓存组关系，给出回收、重置及连续运行等路径的正确性检查记录。
4. 固定输入和生成配置，进行输出 token 对照；按明确的容差或一致性标准记录差异及原因。
5. 完成上述三种场景及无复用开销检查，报告全部请求的结果，同时记录有利场景、无收益场景和退化场景。
6. 分清输入 token 命中、实际输入计算、离线生成耗时和在线 TTFT/吞吐的口径。区分首次计算、淘汰后重算与对齐损失，需要各自的事件证据。
7. 提交模块源码、配置、复现脚本、可公开的测量数据、毕业论文及答辩材料。

验收以模块可运行、行为正确、开销受控、结果可复现为依据。性能收益按测量结果呈现，评价其出现条件与代价。

## 四、已有工作与初步依据

2026-09-30 已使用 Qwen3.5-0.8B、vLLM 0.30.0 完成 19 次独立进程运行，共 2432 个成功请求，包含 9 组原版与 `reuse2` 对照和一次原版重复。每次完整运行包含 128 个请求。

| 场景 | 初步结果 |
| --- | --- |
| 热点与一次性请求混合，生成 32 token | 命中输入 token 从 52,224 增至 69,632；累计生成调用耗时降低 4.07% |
| 热点场景，生成 1 token，三个种子 | 累计生成调用耗时分别降低 8.77%、10.27%、3.70% |
| 混合文档，生成 1 token，三个种子 | 耗时分别变化 -5.24%、+1.25%、-1.55%，收益方向不一致 |
| 缓存充足，生成 32 token | 两种策略命中量相同；候选策略耗时增加 0.75% |

九组对照的 1152 个请求输出 token 哈希全部匹配。第三轮热点短输出的 p95 耗时从 126.04ms 增至 151.63ms，约增加 20.3%，原因尚待归因，是后续工程需要处理的问题。

上述结果支持受控缓存压力下存在保留空间，以及策略在真实引擎中的可实现性。实验采用公开 LooGLE 文档和人为生成的访问顺序、串行请求、固定 KV 配额与 eager 模式；计时为同步后的离线 `generate` 调用耗时。检查点放置、通用线上收益和完整 Marconi 实现仍需各自的验证。

完整数据及限制说明见[服务器初步实验](../data/public/hybrid-prefix-retention/server-20260930/README.md)。
