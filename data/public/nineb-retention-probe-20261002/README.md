# 混合前缀保留诊断（2026-10-02）

固定 Qwen3.5-9B BF16、vLLM 0.30.0、3 GiB KV 预算（186 块，块长 528 token），复现既有压力轨迹中的目标共享前缀。源请求 `segment002-scan2` 建立前缀，后续压力请求回收缓存，再由 `segment007-scan0` 请求同一前缀。

每组 64 个串行请求、固定到达序列，四种设置各从新进程重复两次：原版；预先知道目标并保留完整目标缓存组；仅保留 FullAttention 组；仅保留三个 Mamba 状态组。两轮采用相反顺序。保护只重排空闲队列、不增加容量、不更改引用计数；未来目标已知这一条件只用于诊断因果关系，不是实际可部署策略。

|---|---|---:|---:|---|
|原版（2 次）|0|0|129,360|无|
|只保留注意力（2 次）|FullAttention 组 7 块|0|129,360|无|
|只保留状态（2 次）|Mamba 组各 1 条，共 3 条|0|129,360|无|
|完整保留（2 次）|FullAttention 7 块 + Mamba 三组各 1 条|3,696|133,056|只有目标请求 +3,696|

8 组共 512 个请求，全部成功，每个生成 128 token。两次重复下，请求的输入与输出 token 哈希均匹配。每个设置使用相同的 186 个缓存块；没有保护不足而被迫淘汰受保护块的情况。完整保护没有让其余 63 个请求少命中。本轨迹下获得了目标请求的额外复用，未观察到命中损失转移给其他请求。

**这项结果说明：该混合模型的一段可复用前缀需要 FullAttention 块和 Mamba 状态一起存在；只留下其中一类仍没有缓存命中。** 它补上了“未来会用到的缓存被淘汰，且同容量下完整保留能恢复复用”的可重复案例。结果支持设计一个感知混合缓存组完整性的保留模块。

边界也要说清：总缓存命中量不是精确执行 prefill 量，本轮没有在调度器记录真实重算 token；本次完整保护增加了总命中，但不代表所有压力轨迹都没有置换代价；目标前缀事先已知，8 次单一固定串行轨迹也不证明通用策略收益。它验证了组间完整性依赖，不单独证明收益来自“混合架构相对全注意力模型更差”。下一步是把组完整性加入普通运行策略，并在多个轨迹中观察保护收益与其他请求受影响情况。
